# 回复建议：个人化与简洁度

## 目标

回复建议要像用户本人在这个会话里会发的话，而不是一封完整商务邮件。先解决“要不要回”，再解决“回什么”。

## 本地风格学习

每个安装者都从自己的本地微信记录学习，不使用维护者的统计或示例。先在个人 Profile 的 `owner_aliases` 配置本人微信昵称；无法识别本人发送者时停止模仿，只提供中性草稿并提示完善配置。

滚动分析最近 30 天本人发出的私聊文本，覆盖不同关系和普通联系人，不只读取商单推广、自媒体博主或其他重点标签。统计时排除群聊、链接、附件占位、转发和复制的长文。

- 跨联系人样本只学习长度、分段和标点。
- 当前联系人样本学习确认词、笑声写法、称呼、口语、英文和表情。
- 当前会话至少有 5 条本人消息后才采用专属口语；样本不足时保持中性。
- 数据变化时按滚动窗口刷新，只保留聚合指标，不复制原始私聊到技能、报告或外部系统。

## 生成顺序

1. 刷新并读取当前联系人的最新上下文。
2. 忽略系统消息，检查最后一条对话消息是谁发的。本人已经回复则默认不追发。
3. 判断消息是否只是“好的、收到、谢谢、哈哈、表情”等自然收尾；这类通常不用回复。
4. 识别唯一需要回应的问题、请求或情绪，不复述整段背景。
5. 从当前会话推断关系与语域，再用全局长度习惯约束成稿。
6. 输出一条主回复。只有存在实质不同的决策分支时才给一个备选。

## 关系语域

- **亲近朋友**：沿用双方已有称呼、缩写、英文和表情；可以轻松，但不突然变油腻或煽情。
- **熟人/同辈**：直接回答，省略公文式开场和结尾。
- **熟悉的合作对象**：保留日常语气，同时把金额、时间和下一步说清楚。
- **新商务联系人**：礼貌中性，一次只问必要信息，不堆完整服务介绍。
- **客户/上级/老师**：尊重但具体；只有该会话原本常用“老师”时才沿用。
- **群聊**：考虑旁观者和责任归属；不把适合私聊的亲昵称呼带进群里。

关系不是固定标签。优先使用当前会话近 30—80 条双方消息；长期总体习惯只决定长度、分段和标点，不覆盖当前关系。

## 默认文风

- 一条主回复，通常 1—2 个微信气泡；长度优先贴近本人滚动样本，样本不足时默认不超过 50 个中文字。
- 先直接回答，再补一个必要问题或下一步。
- 少用句号和完整书面段落；是否使用“哈哈、hh、bro、好滴、～、表情”取决于当前会话证据。
- 不重复对方已经知道的方案、背景和理由。
- 避免“老师你好，收到”“我会结合前面的上下文”“为了避免口径偏差”“有需要补充的信息我会集中列出”等模板腔。
- 用户明确要完整报价、合同边界、交付说明或正式邮件时才展开长版。

## 事实门禁

金额、日期、交付范围、授权、付款、完成状态和对外承诺必须来自原消息或用户确认。无法确定时，指出缺哪一个事实；不要用听起来专业的内容填空。

## 开源边界

技能包不得包含维护者或任何使用者的姓名、联系人、绝对路径、聊天原文、个人统计、关系标签或学习结果。公开仓库只保存算法、默认阈值和脱敏测试数据；`profile.local.json`、数据库、缓存、输出报告和风格结果必须保持在 `.gitignore` 中。

## 默认输出

```markdown
建议回：
> 一条可直接发送的短回复

判断：熟悉的合作对象；回应报价；金额待用户确认。
```

若无需回复：

```markdown
不用再回。你已经回复过，等对方下一条。
```
